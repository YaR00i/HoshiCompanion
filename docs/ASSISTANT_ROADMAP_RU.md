# Хоши как помощница в приложениях — проект плана

Дата: 26 сентября 2026 года. Статус: план; первый локальный опыт с голосом реализован, ручная проверка остаётся.

Этот план расширяет [карту интерактивного персонажа](ROADMAP_INTERACTIVE_RU.md). Хоши
сохраняет собственную жизнь, занятия и реакции. Помощь с приложениями добавляет ей
поводы откликнуться и небольшие действия по просьбе пользователя. Присутствие
приложения на экране само по себе не обязывает Хоши комментировать происходящее.

Уточнённый приоритет: сначала попробовать **общаться через Хоши с Codex или
ChatGPT**, затем расширять её знания о браузере и других приложениях. Список
возможностей ниже — направление развития, а не обещание, что одна модель сама
освоит любой интерфейс.

## Как это должно ощущаться

- Пока пользователь работает, Хоши тихо сидит, гуляет или рисует. Если у задачи
  Codex изменился статус, она может взглянуть в сторону карточки и показать
  маленький знак. Подробности открываются по нажатию.
- На карточке текущей задачи видны название, «работает / нужен ответ / готово»
  и переход к задаче. Рядом доступны понятные ручные действия: новая задача и
  разговор с Хоши голосом.
- Когда играет видео или музыка, Хоши может показать название и кнопки
  воспроизведения. Громкость — отдельная команда, только для выбранной
  медиасессии или приложения, после проверки соответствия сессии.
- Календарь может подсказать о ближайшем событии и предложить тихий режим.
  Discord может показать выбранных друзей в сети, если официальный способ
  подключения подойдёт для этого приложения.
- Каждая интеграция выключается отдельно. В тихом режиме важная информация
  остаётся доступной в меню, но Хоши не прерывает работу всплывающими репликами.

Маленькие сценки должны соответствовать событию: при завершении задачи Хоши
откладывает свой карандаш и показывает звёздочку; при ожидании ответа тихо
поднимает руку; под музыку слегка качается; перед встречей заглядывает в
блокнот. Сначала это редкие реакции на достоверные события. Сами приложения
не получают права напрямую запускать анимации или переносить Хоши по экрану.

## Три уровня возможностей

1. **Замечать:** получить ограниченный факт от источника: состояние задачи,
   воспроизведение, время события, статус друга. Факт имеет источник и срок
   годности; устаревшие сведения не показываются как актуальные.
2. **Показывать:** карточка, короткий жест или ненавязчивое уведомление. Текст
   и анимация не должны скрывать рабочий интерфейс и мешать click-through.
3. **Действовать:** открыть задачу, поставить медиа на паузу, начать новый
   разговор, создать событие. Действия с побочным эффектом выполняются только
   после явного нажатия или понятной голосовой команды с подтверждением.

Распознавание краёв окон для перемещения остаётся отдельной задачей. Чтение
содержимого выбранного приложения не превращает текст, видео или кнопку в
безопасную поверхность для прыжка. Контроллер поверхностей продолжает
проверять геометрию и маршрут независимо.

## Источники и реальные ограничения

### Codex

Официальный Codex App Server предоставляет методы списка и чтения задач,
состояние выполнения и события; SDK позволяет запускать и продолжать
собственные задачи. Это подходящая основа для прототипа карточки задач.
Локальная проба показала, что отдельный процесс App Server может прочитать
**эту существующую задачу настольного Codex** по её ID. Список задач тоже
доступен через базу состояния. При этом текущая задача для отдельного
процесса имеет состояние `notLoaded`: живые события и точный статус
выполнения ещё не подтверждены. Доступ ко всем задачам других хостов и
особенности учётной записи также требуют отдельной проверки.

Первый набор: список выбранных задач, статус, «нужен ответ», открытие задачи.
Создание новой задачи и отправка текста — следующий шаг после проверки
авторизации, общего состояния и способа открытия именно нужной задачи.
Не опираться на внутренние инструменты текущего чата Codex как на публичный
API для Хоши.

Источники: [Codex App Server](https://developers.openai.com/codex/app-server),
[Codex SDK](https://developers.openai.com/codex/sdk).

### Браузер и YouTube

Для простого «что сейчас играет» сначала проверить системные медиасессии
Windows: они дают сведения о воспроизведении и команды play/pause, когда
браузер или плеер публикует сессию. Для деталей страницы, вкладки и точных
кнопок нужен необязательный модуль расширения браузера с разрешениями для
конкретных сайтов. Связь расширения с Хоши возможна через Native Messaging.
Общий доступ ко всем сайтам не требуется для первой версии.

Название страницы или ролика может отсутствовать или быть неверным; видео
может не публиковать отдельную медиасессию. Управление громкостью требует
отдельной Windows-интеграции и проверки, какая аудиосессия соответствует
выбранному плееру. Нельзя обещать управление громкостью каждого видео.

Источники: [медиасессии Windows](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessionmanager),
[разрешения расширений Chrome](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions),
[Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging).

### Google Calendar

Календарь подключается через официальный OAuth с минимальным доступом
только на чтение событий. Создание или изменение события — отдельное
разрешение и отдельный пользовательский сценарий. Первая карточка: ближайшая
встреча, время до неё, «открыть календарь», предложение тихого режима.
Тексты и описания встреч не нужны для базового напоминания.

Источник: [разрешения Google Calendar API](https://developers.google.com/workspace/calendar/api/auth).

### Discord

Discord Social SDK описывает список отношений и состояние пользователей;
официальный путь требует регистрации Discord-приложения, подключения учётной
записи и проверки условий использования SDK для Hoshi как desktop companion.
Это исследовательская интеграция: доступность нужных прав и поведение в
реальной сборке ещё не проверены. Первый полезный сценарий — только несколько
выбранных друзей, без чтения переписок. Отправку сообщений и голосовые каналы
планировать отдельно.

Источник: [Discord Social SDK](https://discord.com/developers/docs/social-sdk/index.html),
[начало работы с SDK](https://discord.com/developers/docs/social-sdk/getting_started.html).

### Разговор с Хоши

Есть два проверяемых маршрута:

1. **Обычный ChatGPT Voice на сайте.** Это голосовой разговор из подписки
   ChatGPT. Для Pro $100 справка OpenAI сейчас указывает до 15 часов Live за
   скользящие 24 часа. Небольшое расширение Chrome по ручному нажатию получает
   только громкость звука выбранной вкладки и передаёт число Хоши по локальному
   соединению. Это позволяет пробовать реакцию рта без API-ключа и без
   расходования голосового бюджета настольного Codex. Расширение не даёт Хоши
   текста разговора, фонем или права отправлять команды ChatGPT.
2. **Собственный голосовой разговор Хоши.** Приложение управляет микрофоном,
   звуком и анимацией напрямую через голосовой API. Это даёт больше контроля
   над аватаром и командами, но требует отдельной настройки API и оплаты.

Рекомендация для первого опыта: проверить первый маршрут в Chrome и убедиться,
что Хоши реагирует только на ответы ChatGPT. Это амплитудная анимация, не
точная синхронизация губ по звукам речи. Микрофон включает сам пользователь
в ChatGPT; Хоши не получает к нему доступ. Голос в настольном Codex имеет
отдельную стоимость и расходует бюджет Codex, поэтому для этого опыта не подходит.

Следующая цель — смысловые команды из ChatGPT Voice в Хоши. Live поддерживает
подключённые плагины, но по текущей справке OpenAI личный Pro разрешает
собственные MCP-инструменты в режиме чтения; действия записи доступны в
Business и Enterprise/Edu. Поэтому прямые команды Хоши и создание задач Codex
через собственный инструмент **пока нельзя обещать для этой подписки**.
Проверим доступные штатные интеграции и изменения правил, прежде чем выбирать
другой маршрут. Работа Codex по любой команде всё равно расходует его лимит.
Нельзя выдавать инструмент с изменениями за инструмент только для чтения.

Источники: [ChatGPT Voice](https://help.openai.com/en/articles/20001274-chatgpt-voice),
[стоимость Voice в настольном Codex](https://learn.chatgpt.com/docs/pricing),
[права собственных MCP-инструментов в ChatGPT](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt),
[захват звука вкладки Chrome](https://developer.chrome.com/docs/extensions/reference/api/tabCapture),
[Realtime API](https://developers.openai.com/api/docs/guides/realtime),
[MCP-инструменты](https://developers.openai.com/plugins/concepts/mcp-server),
[раздельная оплата ChatGPT и API](https://help.openai.com/en/articles/9039756).

## Как Хоши узнаёт, что умеет приложение

Универсального списка команд «для любого окна» операционная система не даёт.
Поэтому Хоши собирает картину из нескольких независимых источников:

- официальный API приложения — надёжные данные и действия там, где он есть;
- доступность Windows — названия и роли видимых элементов, если приложение
  раскрывает их;
- расширение браузера — элементы и адреса выбранных сайтов с разрешения
  пользователя;
- один кадр выбранного окна и локальное распознавание — запасной способ
  понять видимое, с обязательной проверкой перед действием.

Каждый адаптер объявляет **возможности**, а не передаёт модели право нажимать
куда угодно: например, `codex.open_task`, `media.pause`, `calendar.show_next`.
У каждой возможности есть входные данные, условия доступности, права и
проверка результата. Неуверенно распознанная кнопка может стать подсказкой
для пользователя, но не автоматическим действием.

Избранные приложения и сайты сначала добавляются вручную: название, способ
открытия, нужные разделы, допустимые действия. Когда этот сценарий станет
удобным, Хоши сможет предлагать часто используемые места по локальной
статистике, с возможностью удалить предложение и не вести такую историю.
Для планера поверх них нужны сохранённые пользователем задачи и короткие
маршруты вроде «открой проект → покажи список → напомни проверить пункт».
Запись или очистка данных в чужом приложении остаётся явным отдельным шагом.

Маленькая AI-модель позже сможет выбирать одну из уже объявленных команд и
заполнять её параметры. Она не придумывает новые права и не получает
произвольного управления мышью. Проверку команды выполняет Хоши, а не модель.

## Общая основа без дублирования поведения

Каждое подключение переводит данные в небольшое событие: `source`, `kind`,
`observed_at`, `expires_at`, `display_summary`, `allowed_actions`,
`permission_level`. Центральный слой контекста решает, актуально ли оно и
разрешено ли показывать его сейчас. Он **не** двигает окно Хоши и не меняет
кости. `companion.gd` координирует показ и ручные действия; существующий
IntentPlanner выбирает допустимую мини-сценку, а pose/controller-слои её
исполняют. Одновременно показывается одна карточка приложения и не более
одной короткой реакции.

Разрешения разделяются по источнику и по уровню: видеть состояние, читать
подробности, выполнять действие. Отключение источника сразу убирает его
данные из активного контекста. При ошибке или отсутствии интернета Хоши
продолжает обычное поведение. Секреты и OAuth-токены хранятся вне Git и
экспорта проекта. По умолчанию не сохранять сырой текст окон, кадры,
аудио и переписки. Для голосового облака отдельно и понятно показывать,
какие данные отправляются наружу.

Это новое разрешаемое пользователем направление для конкретных интеграций.
Действующий геометрический поиск опор и ручной выбор внешнего окна не
получают скрытого чтения содержимого из нового слоя.

## Очерёдность работы и приёмка

### Шаг 0 — короткие технические пробы

- Проверить вживую локальную анимацию рта от ChatGPT Voice в выбранной вкладке
  Chrome; отдельный запуск и ручное подключение расширения описаны в
  [CHAT_VOICE_PREVIEW_RU.md](CHAT_VOICE_PREVIEW_RU.md).
- Проверить, видит ли отдельный App Server те же задачи, что открыты в
  настольном Codex, и можно ли открыть выбранную задачу штатным способом.
- Проверить Chrome/YouTube и другой плеер через медиасессии Windows:
  появляются ли статус, название и команда паузы.
- Проверить, допускает ли Discord Social SDK нужный сценарий для Хоши.
- Результат каждой пробы: «доступно», «доступно с ограничением» или «нужен
  иной пользовательский сценарий» с работающим минимальным примером.

Локальная read-only проба 26.09.2026: handshake прошёл; начальный
`thread/list` с обычным сканированием не ответил за 12 секунд. Повторный
`thread/list` с `useStateDbOnly` вернул первую страницу; `thread/read` по ID
текущей задачи тоже сработал. Ни одна задача не запускалась и не изменялась.
Следующая проба — получить актуальный статус и события без чтения содержимого
разговоров и без вмешательства в работающий настольный клиент.

### Шаг 1 — тихая карточка помощницы

Сделать одну компактную карточку рядом с Хоши, открываемую по нажатию.
В ней источник, актуальный статус, время обновления и максимум два действия.
Первый источник выбрать по результатам шага 0: **Codex**, если есть надёжный
доступ к текущим задачам; иначе **медиа Windows** как полноценный первый
вертикальный срез. Проверка: карточка не перекрывает клики вне собственных
элементов, не всплывает во время переноса и корректно скрывает устаревший статус.

### Шаг 2 — Codex и работа

Добавить список выбранных задач и состояния «работает / ждёт / завершена»,
переход к задаче и лишь затем создание новой. Хоши отмечает завершение или
ожидание ответа одним редким жестом. Проверка: нет ложного «готово», чужая
задача не открывается по ошибке, новое задание не создаётся от автономного
решения Хоши.

### Шаг 3 — медиа и браузер

Показ текущей медиасессии, play/pause и выбор источника. После ручной
проверки добавить регулировку громкости подходящей аудиосессии. Расширение
для YouTube/выбранных сайтов вводить только там, где системных сведений
реально не хватает. Проверка на Chrome, другом браузере и источнике без
медиасессии.

### Шаг 4 — календарь и рабочий ритм

OAuth на чтение, ближайшее событие, тихие напоминания и ручное включение
режима сосредоточения. Проверка разных часовых поясов, события без названия,
отозванного доступа и отсутствия сети. Создание встреч — отдельный срез.

### Шаг 5 — Discord и прочие приложения

После подтверждённой доступности Social SDK показать выбранных друзей в
сети. Реакция Хоши редкая и настраиваемая, чтобы не сообщать о каждом
изменении статуса. Позже можно добавлять отдельные коннекторы для других
часто используемых приложений по тому же контракту событий и разрешений.

### Шаг 6 — голос и совместное поведение

После пробы обычного ChatGPT Voice добавить проверенные смысловые команды,
затем короткий разговор по кнопке через аватар. Хоши может ответить на запрос «что с задачей?» или
«скоро ли встреча?» только из разрешённых свежих данных. Перед передачей
контекста в облачную модель показывать выбранные источники. Ни текст,
ни модель не получают прямого управления окнами, костями или отправкой
сообщений без отдельной проверки действия.

## Ближайшее продуктовое решение

Рекомендация: начать с шага 0, сфокусировавшись на **одном разговоре через
Хоши и одной выбранной задаче Codex**. Первый демонстрационный результат:
нажать на Хоши, перейти к разговору, увидеть состояние выбранной задачи и
получить от неё одну уместную реакцию. Достоверную синхронизацию голоса и
аватара включать только после проверки доступного канала. Затем сделать
тихую карточку и расширять источники. Визуальный вид карточки согласовать
по нативному наброску до длительной реализации.
